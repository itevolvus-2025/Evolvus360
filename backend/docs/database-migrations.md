# Database and migration standards

## SQLAlchemy metadata

`app.database.base.Base` is the single SQLAlchemy 2.x declarative base. Importing
`app.models` imports each model module so mapped classes register in
`Base.metadata`; Alembic uses that metadata for autogeneration. Keep models in
`app.models` and business logic in `app.services`.

The shared metadata names primary keys, unique constraints, check constraints,
foreign keys, and indexes consistently. Check constraints should have explicit
names because the naming convention includes the supplied constraint name.

## Model conventions

- Use `id` as the primary key. New internal entities should normally use a
  PostgreSQL `BIGINT` identity key; use UUIDs when an identifier must be
  unguessable or generated across independent systems.
- Declare foreign keys with an explicit `ondelete` policy. Use typed
  `Mapped[...]` relationships with `back_populates`; avoid implicit cascade
  deletion for records that require audit or retention.
- Add `TimestampMixin` for UTC-aware `created_at` and `updated_at` columns.
  `created_at` has a database default; ORM updates refresh `updated_at`. Direct
  SQL updates must maintain `updated_at` themselves.
- For soft deletion, use nullable `deleted_at` from `SoftDeleteMixin`. Active
  rows have `deleted_at IS NULL`. Queries must filter explicitly; no global
  ORM filter is installed. Use a partial unique index for active-row uniqueness
  only when that rule is required by the business domain.
- Add indexes for measured filter, join, ordering, and uniqueness patterns.
  PostgreSQL does not automatically index the referencing side of a foreign
  key. Add that index when query plans or delete/update workloads need it.
  Avoid duplicate indexes, low-selectivity indexes without evidence, and
  indexing every foreign key by default.

## Alembic workflow

Alembic reads `DATABASE_URL` and pool connection timeout from Pydantic Settings.
`alembic.ini` contains no credentials. Online migrations use a separate
`NullPool` engine and connection; they do not use a request session or the
application request pool. The application never runs migrations on startup.

Create a local `.env` from `.env.example` and set `DATABASE_URL` for the target
database. Keep `.env` out of source control. From the `backend` directory:

```powershell
Copy-Item .env.example .env
# Edit .env and set DATABASE_URL before running migrations.
.\.venv\Scripts\python.exe -m alembic -c alembic.ini current
.\.venv\Scripts\python.exe -m alembic -c alembic.ini revision --autogenerate -m "describe schema change"
.\.venv\Scripts\python.exe -m alembic -c alembic.ini upgrade head
.\.venv\Scripts\python.exe -m alembic -c alembic.ini downgrade -1
.\.venv\Scripts\python.exe -m alembic -c alembic.ini history
```

Review every autogenerated revision before applying it. Migrations must provide
both `upgrade()` and `downgrade()` operations where reversal is safe. Destructive
or data-transforming changes need a deliberate recovery plan; do not assume a
schema downgrade can restore deleted data.

HRMS owns its relational HRMS tables and uses the `alembic_version` table.
Email Service is a separate application with its own migration directory and
uses `email_service_alembic_version`. Both services may point `DATABASE_URL`
at the shared `Evolvus360` database. Each migration environment filters
autogeneration to its own model metadata; migrations must still be reviewed to
ensure they touch only that service's tables. Do not create or restore a
`master_data` table: HRMS roles, permissions, departments, and entities are
modeled as separate relational tables. The compatibility migration restores
recoverable role, permission, and menu rows before removing the legacy table;
it stops without changing data if department/entity ownership cannot be
reconstructed. Relational menu and role-menu tables are retained for existing
records, although the current backend API does not expose them.

Run each service's Alembic commands from that service's directory and virtual
environment. Running one service's migration commands does not advance the
other service's version table.
